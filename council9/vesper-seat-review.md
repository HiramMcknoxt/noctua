## 1. Findings register (most severe first)

### R9-V1 — A detective's "submission" silently rewrites a LIVE hot-list entry — including delisting it. HIGH. (U6)
- **Path:** the non-supervisor branch of `_post_hotlist` inserts the submission with `INSERT ... ON CONFLICT(plate,state,list_source,case_no) DO UPDATE SET category=..., added_by=..., added_ts=..., expires_ts=...` (`janus.py:5041-5052`). The conflict key is the entry's identity, so a submission naming an already-LIVE entry (pending=0) updates that live row in place. The UPDATE never touches `pending`, so the entry never enters the supervisor queue — and the response still says `202 {"result": "submitted"}`.
- **Executed** (`vs_u6_matrix_upsert`): supervisor lists VS6L1 (category "stolen vehicle", no expiry); ingest → ALERT. A detective then submits VS6L1 with the same list and case but category "silver alert" and `expires: "2020-01-01"`. Response: 202 "submitted". The live entry afterwards reads category "silver alert", expires `2020-01-01T23:59:59Z`; it does not appear in `/hotlist/pending`; the next ingest of VS6L1 returns **"stored", not ALERT** — the plate is off the road without any supervisor decision.
- **Why it matters:** U6's entire purpose is that listings are a supervisor decision and a detective's add is only a submission. For every plate already listed, that control does not exist: any detective who knows a live entry's (plate, list, case) triple — ordinary working knowledge — can change its category or kill it with a past expiry (or extend it indefinitely with a future one). The chain records a `HOTLIST_ADD_PENDING` naming the plate_ref, the actor, and the submitted category — but **not the submitted expiry**, so the delisting ingredient itself leaves no chain trace, and nothing in the entry tells a reader it was rewritten by a submission.
- **Fix direction:** a submission must never mutate a live row. On conflict with a pending=0 row, store nothing (the uniform 202 still answers); on conflict with a pending row, updating the submission is fine. Add a discriminating case: detective resubmits a live entry with a past expiry → entry byte-identical, ingest still ALERTs.

### R9-V2 — U1's lockout rule is bypassed on the pickup endpoint: five wrong keys lock any human account. MEDIUM-HIGH. (U1)
- **Path:** `_totp_pickup` authenticates outside `need_auth` by design. Its wrong-key branch (`janus.py:5623`) calls `_auth_lock_note_failure(target)` directly, bypassing `_lockout_counts` (`janus.py:3188-3207`), whose whole rule is that a failure *at* the key never counts. (The bad-token branch at `janus.py:5657` also calls it — correctly: there the key verified, so counting is right.)
- **Executed** (`vs_u1_pickup_wrongkey`): five `POST /auth/2fa/pickup` requests naming det.okafor with a wrong key → the account locked: `ACCOUNT_LOCKED` chained, the detective's valid key + valid TOTP refused 401. Spraying the machine identity the same way locked nothing (the service-role guard inside `_auth_lock_note_failure`, `janus.py:3079ff`, held; ingest kept returning 201). A supervisor unlock (200) restored the account (valid auth 200 after).
- **Why it is not Round 8's C8-01 again:** ingest and the machine identities cannot be locked by any path I found, and two recovery paths work (supervisor unlock; `provision.py unlock`). What survives is the human side of the same attack: any unauthenticated LAN peer who knows a username can lock that human for 15 minutes, renewable — and can lock *every* human, both supervisors included, five requests apiece, leaving the shell break-glass as the only way back in. U1's own docstring states the invariant this breaks: "a failure AT the key is a guess, and guesses must never found a lock" (`janus.py:3193-3196`).
- **Fix direction:** the wrong-key branch should feed `_note_auth_fail` only — exactly as the unknown/disabled-target branch directly above it already does. One line, plus a discriminating case (the battery's `u1_lockout_scope` spray aimed at `/auth/2fa/pickup`).

### R9-V3 — BLOCKED chain entries still carry the raw hit id; the protection join is live. LOW. (= §3 small (iii), executed)
- `janus.py:5160-5164`: a detective's refused verify of a suppressed hit chains `BLOCKED {hit: <raw id>, reason: "suppressed_queue"}`; the ALERT entry (`janus.py:4628-4630`) carries `{hit: <same raw id>, cam, category}`. **Executed** (`vs_u6_blocked_join`): both payloads share hit id 1; a chain reader (the partner `chain_auditor` role) can join them and learn that the felony-warrant hit at CAM-01 is under a protection order. The verify *response* is correctly uniform (409, byte-identical to not-pending) — the leak is chain-side only, to a role that is read-gated by design. Ruled on in §3.2(iii).

### R9-V4 — `_auth_fail_totals` grows without bound. LOW. (= §3 small (ii), code-read)
- `janus.py:2882, 2915-2916`: one dict entry per distinct sprayed username (keyed by `_user_hash`), never pruned. The neighboring tables are bucket-pruned (`_auth_fail_global`, `_auth_fail_counts`), so the omission is visible in the code's own terms. Per-process memory only (a restart clears it), one small entry per request — a slow, unauthenticated growth vector, not a practical crash. Ruled on in §3.2(ii).

### R9-V5 — U9's gate is a single meta row. INFORMATIONAL.

The behavior is right and documented in code; the report sentence is imprecise. I probed this as a suspected finding and cleared it by execution (null-conf read stores NULL, alerts normally, and a NaN redelivery against a live hit still 400s with the hit untouched).
- §2 U4's "the read model keeps the withdrawn_* fields plus `successor_hit`": the link exists in the `hits.superseded_by` column and in the `READ_SUPERSEDED` chain entry (both executed — see below), but the `GET /hits` listing I executed exposes neither field. ## 2. Rulings on the named items (Brief §3)

**§3.1 — U9 interpretation: RATIFY.** The populated-arrival line is the right line, and I executed both sides of it: an arrival locks and *recovers through the ceremony on the same server*; a born-empty install serves; even a hotlist-only arrival locks. The literal reading would refuse ingest on every first run, every demo, and every test fixture ever written for this system — it does not describe a stricter system, it describes an unusable one. The line I would keep is the shipped one: the tightened state arms when a database arrives with history but no provisioning, judged from the database itself, with pre-1.2 chains exempt as upgrades. R9-V5 names the marker's limit honestly; it does not change the ruling.

**§3.2 — Queued smalls:**
- **(i) `/holds/release` out of the fence safety set: FIX-NOW.** Still present (`janus.py:2144-2146`). Releasing a hold during a suspected rollback makes evidence purgeable — a destructive act wearing a safety label. Extend the same change to `/suppressions/release`, which sits in the same set and is the sharper case: releasing a suppression mid-fence un-protects a protected plate's reads. One set edit plus a fence case each.
- **(ii) Bound `_auth_fail_totals`: FIX-NOW.** R9-V4. The bounding pattern already exists beside it; there is no reason to ship an unbounded unauthenticated growth vector, however slow.
- **(iii) Keyed hit references in BLOCKED entries: PILOT-GATE.** R9-V3, executed. The fix (a keyed `hit_ref` mirroring `plate_ref`) is small, but the exposure is bounded today — chain readership is role-gated and the response side is already uniform — so it may land with the pilot gate rather than block code convergence. It must land, or be explicitly waived on the record, before real protection orders are in the system.
- **(iv) Fence the ceremony-state data surface: PILOT-GATE.** Code-read confirmed: no route-level fencing exists — in ceremony state `auth()` returns the record on the key alone (`janus.py:~3295`) and searches, Tier 3, shares, and reports all serve. The window is real (data can arrive by ingest before enrollment completes, and two key-only supervisors could complete a Tier 3 approval with no second factor at all), but it is bounded: the state is named in /health throughout, and a born-empty install holds only what ingest brought it. The full fix touches every first-boot flow and fixture and deserves its own commissioned item with discriminating cases, not a squeeze-in. For the pilot: go-live must require provisioning completed *before* ingest is connected, as a checklist gate, with the code fix commissioned for the pilot build.
- **(v) 24-hour expiry on pending pickups: CLOSED — already implemented by U7; no action.** The token window is 24 h from `enrolled_ts` (`janus.py:~5643-5652`), and I executed it: with the store aged 72 h, pickup with the correct key and token returns 401. The pending entry itself lingers past the window but is inert — pickup is impossible and a fresh re-enrollment supersedes it. Nothing remains to fix, gate, or declare cannot-do.
- **(vi) enroll-2fa shell-operator honesty gap: CANT-DO — adopt the classification; the document entry is still owed.** I read `docs/CANT-DO.md` in full: the openssl-PATH residual is there, the enroll-2fa entry is **not**. The substance is correct — whoever can run the shell tool holds every confirmer's secret, and no code change fixes that without encrypting the store (which moves the problem rather than solving it). The entry should be added in the post-convergence document loop, beside the openssl entry, in the same plain register.

**§3.3 — S10 null-tolerance: ACCEPT, as a test-only fix.** The orchestrator's characterization matches everything I can check: four full-battery runs, exactly one null sample in five each time, the freshness property true in every returned sample, standalone passes repeated on both sides, and the baseline still fails the case outright (all samples true). A dropped response under six saturating ingest threads on this VM class is a harness sampling artifact. The retry must stay narrow — retry a *null* (no response) once; a returned-but-wrong value still fails — and with that shape the case keeps its teeth.

**§3.4 — R-F diffs: RATIFY, and ratify the practice as standing process.** I read all thirteen diffs in `pack-claude/08-rf-diffs.txt` in full. No assertion line appears as a changed line in any of them. **§3.5 — U6 validation order: RATIFY.** Shipped order (`janus.py:4935-5052`): role → case gate → plate presence → **registry → supervisor suppression refusal → category → expiry → role split**. My executed matrix covers the leak-relevant cells: registry precedes suppression for *both* roles (bogus list = identical 400 for protected plates too), the supervisor's refusal precedes category/expiry validation (protected + thin body = 403 — informative only to the one role allowed the reason), and for non-supervisors every validation precedes the uniform 202 and is plate-independent (missing category and bad expiry are uniform 400s across all three plate classes).
