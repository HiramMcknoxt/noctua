Findings register (most severe first)

F1 — U2: the fence transition mutates and commits state before the chained audit entry, and swallows the chain failure (audit gap on a security event). In _anchor_apply, the clear path is: db.execute("DELETE FROM meta WHERE key='anchor_mismatch'"); db.commit(); w = witness_state(); try: chain.append("ANCHOR_CLEARED", { ... }) except Exception: pass — and the set path is: _meta_set("anchor_mismatch", json.dumps(d)); try: chain.append("STARTUP_ANCHOR_MISMATCH", { ... }) except Exception: pass. _meta_set itself does db.execute(...) + db.commit(). So in both directions the security-state change is persisted and committed first, and the chain entry that is supposed to record it is best-effort and its exception discarded. A chain failure (sink error, DBLOCK contention, scrub refusal) leaves the fence set or cleared with no chained record at all — precisely the class of "unlogged security transition" the project's chain discipline exists to prevent. Order must be reversed (chain the event, then commit the meta change in the same transaction) or the append failure must abort the state change. This is on the headline U2 surface ("fence exit").

F2 — U11 version sweep is demonstrably incomplete: migration/health still stamp 1.2.5 on a 1.2.6 build. VERSION = "1.2.6" is correct at the top, but inside _migrate_124: chain.append("MIGRATION_DEFECT", { "unit": d["unit"], "error": d["error"], "message": d.get("message", ""), "to": "1.2.5"}); chain.append("MIGRATION", { "to": "1.2.5", "defects": len(defects), **counts}); status = { "version": "1.2.5", "state": "incomplete" if defects else "complete", ... So every MIGRATION / MIGRATION_DEFECT chain entry and the migration_status blob surfaced in /health misattribute the repair to 1.2.5. U11's first item was literally "version sweep to 1.2.6." This is a verifiable forced-change miss, not a judgment call. (Grep target: the three literals "1.2.5" in _migrate_124.)

F3 — U2: _anchor_apply clears a checkpoint_disagreement on any clean evaluation, with no check of the prior reason, so deleting the offending checkpoint line clears the fence without the two-key ceremony. try: prior = json.loads(recorded) except ValueError: prior = {}; db.execute("DELETE FROM meta WHERE key='anchor_mismatch'"). The function comment claims the clear is for "a file-state problem the operator can repair" and that a disagreement clears "ONLY when … accepted … or removed." The code does not gate on prior.get("reason") at all — any clean eval clears any recorded mismatch. "Removed" means: an actor with write access to the checkpoints file can delete the disagreeing line, the next 5-second evaluation is clean, the fence clears, and the data surface reopens. ANCHOR_CLEARED does record prior_reason, so it is auditable post-hoc — but the two-key _anchor_accept path is bypassed for the file-edit route. At minimum this deserves an explicit design ruling; as written it does not match its own comment.

F4 — boot path can deadlock the data surface behind a signing outage while claiming the opposite. SIGNING_PUB_PEM = None on ensure_signing_key failure, with the comment "disables signing, not the service." But _checkpoint_sig_ok returns False whenever SIGNING_PUB_PEM is falsy: ok = bool(SIGNING_PUB_PEM) and bool(cp.get("pubkey")) ... so once any checkpoint exists, every checkpoint is "bad," _anchor_evaluate returns a mismatch, the fence engages, and the data surface is 503 — i.e., the service is not merely "signing-disabled," it is fenced. For a fresh install with no checkpoints this is benign (not cps → no mismatch). The behavior is arguably correct fail-closed, but the boot comment is false and an operator reading the log will be misled about the state. Low severity, but it is exactly the "what does the message actually mean" honesty theme.

F5 — potential R4 regression, needs dispatch verification (I cannot see dispatch): anchor_fenced() calls _anchor_apply, which does db.commit() and chain.append(...). If the live 5-second cadence is invoked from anchor_fenced() outside DBLOCK (e.g., from a request handler or a health poll before the lock), this reintroduces the R4/S10 hazard the code repeatedly warns about ("no out-of-lock side effects"; _flush_config_chain explicitly refuses to write when db.in_transaction). I flag it as needs-verification against the dispatch code I was not given — not a confirmed finding.

Rulings on §3

§3.1 — U9 interpretation: RATIFY, conditionally. I cannot see _unprovisioned_locked, so I rule on the line, not the implementation. The literal reading is self-contradictory with the battery (every fixture is born-empty and must ingest/auth key-only), so it cannot be the intended line. Populated-arrival — "a DB that arrived WITH history but no TOTP provisioning, not born empty under this code, with a legacy-chain exemption" — is the defensible boundary: it targets the actual threat (a database copied in from elsewhere with existing plate history and no enrollment ceremony) while leaving the legitimate born-empty operating state alone. Ratify, contingent on: (a) the install_born_empty marker being durable and not writable by an unprivileged path, and (b) /health naming the armed state (unverifiable here). I would not reject it; the alternative (any populated DB serves no key-only human access) breaks first-boot provisioning and every demo fixture.

§3.2 — queued smalls: (i) /holds/release out of the anchor-fence safety set — FIX-NOW. Confirmed present in the safety set: ANCHOR_FENCE_SAFETY_POST = {..., "/holds", "/holds/release"}. Releasing a hold makes evidence purgeable during a suspected rollback; it is destructive and must not ride the safety-write exemption. (ii) bound _auth_fail_totals growth — FIX-NOW. Unauthenticated memory growth keyed on attacker-chosen usernames is a cheap DoS; I cannot see the structure but the vector is real and the fix is small (cap + LRU/eviction). Treat as deployment-gating. (iii) keyed hit references in BLOCKED chain entries — FIX-NOW. Partner-readable chain joined to protected hits is a suppression-oracle leak against the system's core promise. The chain already carries keyed refs elsewhere; this is consistency, not new design. (iv) fence the data surface during T1 ceremony — FIX-NOW. The T1 ceremony is a provisioning window; serving searches/Tier 3/shares/reports through it is the same class of gap T3 closed for the anchor. Small. (v) 24-hour expiry on pending secret pickups — FIX-NOW. An unexpired one-time pickup token is a standing credential; a day bound is the obvious ceiling. (vi) enroll-2fa shell-operator honesty gap — CANT-DO (documentation entry). Correct: whoever runs the shell tool holds the TOTP secret and can compute any confirmer's code; two-key in the shell cannot be cryptographically enforced against the shell operator. Document it as a named limit; do not pretend the ceremony is stronger than it is.

§3.3 — S10 null-tolerance: accept as a test-only fix, with a scoped guard. A dropped /health sample is a real product answer-gap, not pure noise — a monitoring endpoint that returns null under load is itself a health-signal failure. But the disclosed artifact is confined to full-battery saturation, the freshness property held in every returned sample, and the case passes standalone. So: accept the single retry, provided the retried sample is the only tolerated null and the case still fails on a dropped sample that occurs outside the saturation window (i.e., the retry is explicitly scoped to the saturation artifact, not a blanket tolerance). A blanket null-tolerance would be holding the wrong line.

§3.4 — R-F diff review: practice RATIFIED; diffs UNVERIFIED by me. I was not delivered 08-rf-diffs, so I cannot inspect byte-unchanged assertions. The practice — assert bytes unchanged, only change follows a commissioned custody change, diff attached — is sound standing process and should be ratified on its own terms. But ratification of the practice is not ratification of any particular diff; the orchestrator must confirm the diffs mechanically.

§3.5 — U6 validation order: RATIFY with a leak caveat. registry → supervisor suppression refusal → category/expiry → role split is defensible: registry validation before suppression avoids spending suppression state on an unregistered list name, and the uniform-202 for non-supervisors (U6) means the suppression refusal is not a disclosure oracle. The leak to watch: if the registry check returns a distinct error to a non-supervisor before the uniform 202 is emitted, an unauthenticated/unauthorized caller can probe list-registry membership. That is list-name existence, not plate suppression, so it is a minor oracle — but the handler must ensure the non-supervisor path emits the same uniform 202 regardless of registry outcome. I cannot verify the handler; ratify conditionally on that.
